What the Lean proofs actually say

A small, standalone reading guide. Each card starts with the human claim, shows the exact Lean statement, then explains the proof and its limits.

How to read one theorem

theorem names a claim : means “has proposition” := by begins the proof native_decide computes a finite claim ∀ means “for every” ≠ means “is not equal to”

Read everything before := by as the contract. Everything after it explains why Lean accepts that contract. Lean checks the contract for every value allowed by its parameters—not just a few test examples.

Inventory privacy

Another account is always denied

universal

For any actor, owner, player, item, slot, and inventory: if actor and owner differ, equipping returns notOwner.

  1. Parameters: the theorem quantifies over every possible input.
  2. Assumption: different : actor ≠ owner.
  3. Conclusion: the result is exactly the authorization error.
  4. Proof: simplifying equipInventory with the inequality selects its first rejection branch.

Does not prove Hanko itself is secure. It proves the pure policy, while Convex integration tests verify the generated endpoint uses authenticated identity.

Show Lean
theorem otherPlayerCannotEquip
    (actor owner : AuthId)
    (playerId : PlayerId)
    (requestedItem : ItemId)
    (slot : EquipmentSlot)
    (items : List Item)
    (different : actor ≠ owner) :
    equipInventory actor owner playerId requestedItem slot items =
      .error .notOwner := by
  simp [equipInventory, different]

Other inventories cannot change your result

privacy

If two database states contain the same items for this player, the inventory response is identical—even when every other player’s items differ.

  1. The premise equates the player-owned subset in the “before” and “after” states.
  2. The response filters both states by the authenticated player’s ID.
  3. Substitution with that premise makes both responses identical.

This is stronger than “access is denied”: it says unrelated private data cannot influence the authorized result.

Show Lean
theorem otherInventoriesAreNoninterfering
    (actor : AuthId) (player : Player)
    (before after : List InventoryItem)
    (sameOwnedItems :
      before.filter (fun item => item.playerId = player.id) =
      after.filter (fun item => item.playerId = player.id)) :
    readInventory actor player before =
      readInventory actor player after := by
  simp [readInventory, sameOwnedItems]

Road topology

The bridge is traversable only forward

computed

The declared road permits 12 → 13 and rejects 13 → 12.

  1. availableRoads includes every road originating at the current node.
  2. It includes the reverse direction only when bidirectional is true.
  3. native_decide evaluates the finite, Lean-authored graph and checks both propositions.

These two theorems concern this declared one-way bridge. everyRoadEndpointExists separately ensures every road points to real nodes.

Show Lean
theorem oneWayBridgeAllowsForward :
    canTraverse 12 13 = true := by
  native_decide

theorem oneWayBridgeRejectsReverse :
    canTraverse 13 12 = false := by
  native_decide

Random-event frequency

Exactly the favorable buckets hit

counting

If a chance has favorable winning buckets out of possible, traversing every valid bucket produces exactly favorable hits.

  1. Split the range into values below favorable and the remainder.
  2. Show the first part is retained by the hit filter.
  3. Show the remainder is discarded.
  4. The retained range has length favorable.

This proves the bucket mapping has the intended frequency. It does not prove a pseudo-random sequence is statistically independent or cryptographically unpredictable.

Show Lean
theorem exact_favorable_bucket_count (chance : Chance) :
    ((List.range chance.possible).filter
      fun roll => hits chance roll).length = chance.favorable := by
  have split : chance.possible =
      chance.favorable + (chance.possible - chance.favorable) := by
    exact (Nat.add_sub_of_le chance.valid.2).symm
  rw [split, List.range_add, List.filter_append]
  -- The proof then keeps every favorable bucket and
  -- discards every bucket in the remaining suffix.

Combat choices

Every committed charge has all three matchups

table invariant

High charge, side charge, and leap each have at least one weak, neutral, and strong defensive matchup.

  1. Iterate over all committed attacks.
  2. Search all guard positions for each matchup category.
  3. Compute the complete finite table inside Lean.

This proves structural variety in the table, not that the multipliers are perfectly balanced or fun.

Show Lean
theorem everyChargeHasWeakNeutralStrong :
    committedCharges.all (fun attack =>
      guards.any (physicalMatchup attack · = .weak) ∧
      guards.any (physicalMatchup attack · = .neutral) ∧
      guards.any (physicalMatchup attack · = .strong)) = true := by
  native_decide

Catalog guarantees

Small facts prevent broken generated data

generation

Every elemental loadout has two techniques, encounter weights and enemy health are positive, and every road references existing nodes.

These are deliberately modest theorems. Their value is that malformed Lean data cannot generate a deployable TypeScript catalog while the proof gate is active.

A catalog theorem checks its stated property only. For example, positive enemy HP says nothing about whether that enemy is beatable.

Show representative Lean
theorem loadoutsContainTwoTechniques (element : Element) :
    [(loadout element).1, (loadout element).2].length = 2 := by
  simp

theorem enemiesHavePositiveHealth :
    enemies.all (fun enemy => 0 < enemy.hp) = true := by
  native_decide

theorem everyRoadEndpointExists :
    roads.all (fun road =>
      nodes.any (fun node => node.id = road.origin) ∧
      nodes.any (fun node => node.id = road.destination)) = true := by
  native_decide
