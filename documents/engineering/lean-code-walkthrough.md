# How Mythroads is defined in Lean, and how it reaches Convex

This document explains the Lean sources under [`proofs/`](../../proofs) and the path they take to
the TypeScript that Convex runs. It assumes no prior Lean experience.

The shortest useful model is:

> The game is one pure function in Lean. Everything else either supplies its vocabulary, proves
> something about it, or compiles it — and the code Convex executes is generated from it, never
> written beside it.

Convex still runs TypeScript; it does not run Lean inside a transaction. What changes is where the
rules are authored, and what can be said about them before they ship.

A rendered, always-current index of every declaration in `proofs/` — signatures, docstrings, source
and the axioms behind each theorem — is generated by `npm run docs:lean` into
[`lean-definitions.html`](lean-definitions.html), and served by the application at `/lean`.

## The shape of the thing

One game definition, from the Lean files that hold it to the Convex module that runs it:

```text
proofs/Mythroads/Game/**        catalogues: board, items, magic, enemies, encounters, RNG, turn order
          │
          ▼
proofs/Mythroads/Engine/**      THE GAME: State, Event, Effect, Error, step — and its theorems
          │
          ├──lake exe mythroads-compile──▶  shared/generated/engine.generated.ts
          │                                 (step itself, compiled from LCNF)
          │
proofs/Mythroads/Backend/Aggregate/**   the interpreter around it, as Lean values
          │
          ├──lake exe mythroads-emit────▶  convex/generated/aggregate/{load,rows,persist,
          │                                 envelope,enums,boundary}.generated.ts
          │                                 boundary = loadState → step → saveState
          │
          └──lake exe mythroads-emit────▶  convex/generated/game-api.generated.ts
                                            (authorize → deduplicate → applyGameEvent → persist)
                                                       │
                                            convex/game.ts — two adapter lines
                                                       ▼
                                            the Convex JavaScript runtime
```

Four executables read that tree, and they are the only ones:

| Executable | Root | What it writes |
|---|---|---|
| `mythroads-emit` | [`proofs/Emit.lean`](../../proofs/Emit.lean) | every `*.generated.ts` Convex module |
| `mythroads-compile` | [`proofs/Compile.lean`](../../proofs/Compile.lean) | `shared/generated/engine.generated.ts` |
| `mythroads-oracle` | [`proofs/Oracle.lean`](../../proofs/Oracle.lean) | `tests/engine/fixtures/engine-oracle.json` |
| `mythroads-docs` | [`proofs/DocExport.lean`](../../proofs/DocExport.lean) | the JSON behind `lean-definitions.html` |

## A very small Lean primer

| Lean | Meaning |
|---|---|
| `namespace Mythroads.Engine` | put the following names under a common prefix |
| `structure X where` | a record with named fields, like a TypeScript interface |
| `inductive X where` | a choice between named cases, like a discriminated union |
| `def name : Type := value` | define a value or function |
| `abbrev NodeId := Nat` | a transparent alias for an existing type |
| `Option X` | either `some value` or `none` |
| `Except E A` | either `.error e` or `.ok a` |
| `match x, y with` | exhaustively select behaviour for every combination of constructors |
| `theorem name (…) : claim := by …` | state a proposition and prove it |
| `#guard e` | evaluate `e` at compile time and fail the build if it is not `true` |

A `theorem` is not a test. `simp [permitted] at h` is a proof step, and the claim it closes holds
for every value the types admit — every room, every actor, every string — which no test suite can
do. A `#guard` is the opposite and is used deliberately for concrete data: it evaluates one
expression during elaboration, adds no declaration and no axiom, and fails the build if it is
false.

## 1. Four types and one function

Everything in [`Engine/Core.lean`](../../proofs/Mythroads/Engine/Core.lean) exists to let one
function be written.

**`State`** is the room, and the room is the whole aggregate: one room is one transaction, one
event log, one state. Heroes are a list inside it, so `turn : Nat` can be *proved* to name a real
hero rather than checked at runtime.

```lean
structure State where
  code : String
  host : Mythroads.AuthId
  players : List PlayerState
  turn : Nat
  round : Nat
  phase : Phase
  message : String
  lastRoll : List Nat
  rng : Nat
  rngCounter : Nat
  camera : Option Camera
  version : Nat
```

`rng` is worth pausing on: randomness is a field of the state, advanced by
`State.draw`, never sampled ambiently. That is what makes replay faithful.

**`Phase`** is the turn-structure automaton, and it carries its payload:

```lean
inductive Phase where
  | lobby
  | awaitingRoll
  | moving (moves : Nat) (selection : Option Selection)
  | combat (battle : CombatState) (stage : CombatStage)
  | encounter (drawn : EncounterState)
  | shop (kind : Inventory.ShopKind)
  | finished (winner : Mythroads.PlayerId)
```

Because `Phase.combat` carries the whole battle, "is there a combat row for this room?" is not a
question the rules can ask — an inconsistent state does not typecheck. The Convex `rooms.phase`
column is narrower than this inductive, and `Phase.name` is exactly that erasure.

**`Event`** ([`Engine/Event.lean`](../../proofs/Mythroads/Engine/Event.lean)) is the alphabet: one
constructor per wire event type, sixteen of them, from `roomCreate` to `cameraZoom`. Four total
functions classify every constructor — `Event.name`, `Event.authority`, `Event.durable`, and
`permitted` — so adding a constructor without classifying it is a compile error rather than a
runtime hole. `Envelope` wraps an event with the facts the client is not allowed to assert:

```lean
structure Envelope where
  actor : Mythroads.AuthId
  subject : Option Mythroads.PlayerId
  event : Event
  seed : Nat
```

`actor` is derived server-side from the auth token, and `seed` is entropy supplied by the trusted
boundary and stored in the log.

**`Effect`** is what the pure function asks the outside world to do afterwards: `persistPlayer`,
`persistRoom`, `persistCombat`, `persistEncounter`, `persistSelection`, `clearSelection`,
`persistCamera`, `appendLog name`, `notify message`. The row-writing ones carry the row they
describe rather than pointing back at the new state, because a single step can open a battle and
close it, leaving the state past the row the interpreter still has to write.

**`Error`** enumerates every refusal, from `unauthorized` to `cameraNotFree`. Each maps to one
`ConvexError` at the boundary through `Error.message` in
[`Engine/Message.lean`](../../proofs/Mythroads/Engine/Message.lean), a table keyed on both the
error and the event — because the same refusal reads differently depending on what was asked, and
those sentences are pinned verbatim by the golden-master suite.

The two together give the result type of the whole game:

```lean
abbrev Outcome := Except Error (State × List Effect)
```

And the function, in [`Engine/Step.lean`](../../proofs/Mythroads/Engine/Step.lean):

```lean
def step (s : State) (env : Envelope) : Outcome :=
  if !authorized s env then .error .unauthorized
  else if !onTurn s env then .error .notYourTurn
  else if !permitted s.phase env.event then .error .wrongPhase
  else transition s env
```

Note what the *type* says: no `IO`, no clock, no ambient generator. There is nowhere for a hidden
input to enter, which is why determinism needs no argument beyond the signature.

## 2. The three gates

They are three separate predicates on purpose.

* **`authorized`** asks whether the verified actor holds the privilege the event demands:
  `.account` needs any verified identity, `.roomHost` compares against `State.host`, and
  `.playerOwner` compares against the addressed hero's stored `owner`. None of those three values
  ever comes from the client body.
* **`onTurn`** asks whether the envelope's subject is the hero whose turn it is. Lobby events and
  `inventory.equip` are exempt; camera commands are *not*, because the shared view is driven by
  whoever is playing.
* **`permitted`** is a single table on `(phase, event)`. Read top to bottom it is the game's
  turn-structure specification:

```lean
def permitted (phase : Phase) (e : Event) : Bool :=
  match phase, e with
  | _, .inventoryEquip _ _ => true
  | _, .cameraToggle | _, .cameraMove _ | _, .cameraZoom _ => true
  | _, .playerJoin _ _ _ => true
  | .lobby, .roomCreate _ | .lobby, .gameStart => true
  | .awaitingRoll, .movementRoll => true
  | .moving _ _, .movementSelect _ => true
  …
  | _, _ => false
```

Keeping them apart is what makes the security theorems one-liners, and it is why they are worth
reading before anything else in the engine.

## 3. Phase dispatch

`transition` is one flat match on `(phase, event)`. Every arm hands the phase payload to a
per-phase module under `Engine/Step/`, which therefore never re-checks authority, never re-reads
the turn, and never inspects `Phase` again — its preconditions arrive as arguments:

```lean
def transition (s : State) (env : Envelope) : Outcome :=
  match s.phase, env.event with
  | _, .inventoryEquip row slot =>
      withSubject s env.subject fun p => Shop.equip s env.actor p row slot
  | .awaitingRoll, .movementRoll => withActive s (Movement.roll s)
  | .moving moves selection, .movementStep destination =>
      withActive s fun p => Movement.stepMove s p moves selection destination
  | .combat battle .attackerChoice, .combatAttack choice =>
      withActive s fun p => Battle.attack s p battle choice
  | .shop kind, .shopBuy itemId => withActive s fun p => Shop.buy s p kind itemId
  …
  | _, _ => .error .wrongPhase
```

The modules are `Step/Lobby`, `Step/Movement`, `Step/Landing`, `Step/Combat`, `Step/Encounter`,
`Step/Shop` and `Step/Camera`. A domain error such as `insufficientGold` is still possible inside
them; the gates only settle who may speak and when.

Underneath, [`Engine/Room.lean`](../../proofs/Mythroads/Engine/Room.lean) supplies deliberately few
operations: a total board lookup (`node`, falling back to the castle exactly as the generated
`getNode` does), and **two mutation primitives**.

```lean
def mapPlayer (s : State) (pid : Mythroads.PlayerId) (f : PlayerState → PlayerState) : State :=
  { s with players := s.players.map fun p => if p.id = pid then f p else p }
```

`State.mapPlayer` is the only way a hero changes; `State.advanceTurn` is the only way the turn
moves. That restraint is the whole proof strategy.

## 4. The invariant, and what the theorems actually guarantee

[`Engine/Invariant.lean`](../../proofs/Mythroads/Engine/Invariant.lean) states the safety property
every reachable room satisfies:

```lean
structure Ok (s : State) : Prop where
  heroes : ∀ p ∈ s.players, p.hp ≤ p.maxHp
  turnInRange : s.turn < max 1 s.players.length
```

Two more safety properties are absent because they are free: gold is a `Nat`, so it cannot go
negative, and hero identity survives because every rewrite goes through `mapPlayer`.

Because there are only two primitives, invariant preservation is two lemmas — `ok_mapPlayer` and
`ok_advanceTurn` — plus a one-line side condition per event (`damaged_bounded`, `spent_bounded`,
`restored_bounded`). [`Engine/Preservation.lean`](../../proofs/Mythroads/Engine/Preservation.lean)
carries one lemma per transition, and the dispatcher theorem in
[`Engine/Theorems.lean`](../../proofs/Mythroads/Engine/Theorems.lean) is a mechanical `split` with
one arm per dispatch case. An event added to `transition` without its lemma leaves an arm the proof
cannot close — the build fails.

What is proved, in five families:

| Family | Statement, in English |
|---|---|
| Determinism | `step` is a function of the room and the envelope, and its type admits no other input. |
| Gate theorems | A successful `step` implies the actor held the authority (`step_ok_authorized`), that it was that hero's turn (`step_ok_onTurn`), and that the phase accepted the event (`step_ok_permitted`) — for every state and every actor. |
| Phase safety | Facts about the `permitted` table alone: an attack is only accepted while a battle owes an attacker choice, a purchase only inside a shop, `game.start` only in the lobby, a resolved battle accepts nothing further. |
| Invariant preservation | `Ok` survives `step` (`ok_step`), one logged envelope (`ok_applyLogged`), and a whole replay (`ok_replay`). |
| Camera safety | Camera commands are accepted in every phase, are never durable, and cannot touch the hero list. |

Here is a gate theorem in full; it is representative of the family:

```lean
/-- A successful transition proves the actor held the authority the event demands. -/
theorem step_ok_authorized {s s' : State} {env : Envelope} {fx : List Effect}
    (h : step s env = .ok (s', fx)) : authorized s env = true := by
  by_cases ha : authorized s env
  · exact ha
  · simp [step, ha] at h
```

What this does **not** claim: that Convex, Hanko, V8, the Lean kernel, or the emitters are correct.
Those remain the trusted computing base. The claim is that the rules the generators consume are the
same values the theorems talk about.

[`Engine/Examples.lean`](../../proofs/Mythroads/Engine/Examples.lean) complements the theorems with
compile-time `#guard`s that walk a full turn, a battle round and a shop visit — concrete evidence
that the abstract statements describe a game somebody can actually play.

## 5. Replay: the log is the truth

[`Engine/Replay.lean`](../../proofs/Mythroads/Engine/Replay.lean) is thirty lines and settles the
persistence model.

```lean
def applyLogged (s : State) (env : Envelope) : State :=
  match step s env with
  | .ok (s', _) => { s' with version := s.version + 1 }
  | .error _ => s

def replay (s : State) (log : List Envelope) : State := log.foldl applyLogged s
```

Rejected envelopes are never appended, so folding a log is total. `replay_append` proves that
replaying a concatenation is replaying the parts, which is precisely what makes **snapshots sound**:
a snapshot taken at version *n* plus the tail of the log equals a replay from the beginning, so a
snapshot table can be added later without weakening a single claim made today. `replay_snoc` is the
one-event corollary — appending one event advances the cached state by exactly one `step`, which is
what a Convex mutation does inside one transaction.

## 6. Effects, and the load–step–save boundary

`step` performs no writes. It returns them.

That splits the backend cleanly in two. The pure half decides; the impure half is a fixed
interpreter that (1) loads the room and its rows into a `State`, (2) calls `step`, (3) on `.error`
raises the matching `ConvexError` and writes nothing, and on `.ok` performs each `Effect` in order
and appends the envelope to `gameEvents` when `Event.durable` says so. Nothing in that interpreter
is game-specific: it is a `switch` on nine constructors.

**That interpreter is what Convex runs.** `api.game.dispatch` authorizes the caller, deduplicates
the `commandId`, and hands the event to `applyGameEvent`, which is the whole write side:

```ts
const roomId = await roomIdForEvent(ctx, event)
const before = await loadState(ctx, roomId)
const envelope = envelopeFrom(event, actorFor(event, actorAuthId, before), 0)
const outcome = step(before, envelope)
if (outcome._ === 'error') throw new ConvexError(Error_message(outcome.a, envelope.event))
const saved = await saveState(ctx, roomId, before, outcome.a.fst, outcome.a.snd)
```

There is no per-event branch below that line. `loadState` reads eight rows into a `State`,
`saveState` interprets the `Effect` list, and the refusal text comes from `Engine.Error.message`,
a Lean table compiled into the engine beside `step` so the sentence a player reads and the reason
the rules gave are the same value. The six modules that emit this live in
[`proofs/Mythroads/Backend/Aggregate/`](../../proofs/Mythroads/Backend/Aggregate) and write
`convex/generated/aggregate/**`; they replaced fourteen per-event handler modules and contain no
rule at all.

Two effects carry more than a name. `persistCombat` carries the battle row and its stage, and
`persistEncounter` carries the drawn encounter, because a transition may open a battle and close it
in the same step — `combat.attack` that empties the enemy writes the final battle row *and* passes
the turn — so by the time the interpreter runs, `State.phase` has moved on and the row it must
write is no longer reachable from the state.

Two behaviours are still **not** rules, and the boundary carries them as declared policies rather
than smuggling them into the engine:

* the **2200 ms encounter reveal delay**, which reads a wall clock and a stored `createdAt`; a rule
  that consulted either would make the same log replay into different rooms;
* the **room-code collision retry**, which needs a database read. The boundary redraws using the
  engine's own `Lobby.roomCode`, four characters and four generator ticks at a time, so the room's
  generator ends where the rules would have left it.

Convex row identifiers are the boundary's for the same reason: a hero the rules have just seated
carries a placeholder id until `saveState` inserts the row and reports the real one back.

## 7. The typed Convex embedding

`proofs/Mythroads/Convex/**` is a picture of the Convex programming model inside Lean, built so
that a generated file cannot say something Convex will reject.

* [`Ty.lean`](../../proofs/Mythroads/Convex/Ty.lean) is **one value universe with two denotations**.
  A Convex value shape has to appear twice in the output — as a runtime validator `v.object({…})`
  and as a static type — and there used to be three unrelated sources for that pair. `Ty.validator`
  and `Ty.tsType` fold the *same* value, so the two cannot drift. The fold is where the platform
  subtleties live: `.optional` inside an object becomes `name?: T`, never `name: T | undefined`,
  because Convex does not transport `undefined`; `.id table` becomes `Id<'table'>`; `.int64` is
  `bigint`.
* [`Table.lean`](../../proofs/Mythroads/Convex/Table.lean) closes the table enumeration and indexes
  `Index` *by* its table, so `Index.playerItemsByPlayerId` cannot be handed to a query over
  `.rooms` — that is a type error rather than a runtime surprise.
* [`Query.lean`](../../proofs/Mythroads/Convex/Query.lean) builds `ctx.db` calls from those types.
  `indexedRead` zips `Index.fields` with the supplied keys, so an emitter cannot name a field the
  index does not have or put the keys in the wrong order. Every unbounded `.collect` carries the
  reason it is allowed, written into the Lean source.
* [`Ast.lean`](../../proofs/Mythroads/Convex/Ast.lean) and
  [`TypeScript.lean`](../../proofs/Mythroads/Convex/TypeScript.lean) are the target syntax tree and
  its printer, and [`Doc.lean`](../../proofs/Mythroads/Convex/Doc.lean) is the layout layer between
  them. Every line break is authored explicitly rather than chosen from a width, because generated
  files are byte-compared. Final style — line width, trailing commas, import order — is Biome's job.
* [`Module.lean`](../../proofs/Mythroads/Convex/Module.lean) makes a whole generated file data:
  a provenance comment, a merged and ordered import block, and a list of items.

## 8. One emitter

[`proofs/Emit.lean`](../../proofs/Emit.lean) is the single code generator. It replaced twenty-nine
`lean_exe` targets that each printed one file to standard output — twenty-nine root modules for
Lake to link, twenty-nine process spawns for the drift check, and a twenty-nine entry duplicate of
the path table living in JavaScript where a wrong relative path could not be caught by anything.

Now the table is a Lean value:

```lean
def outputs : List (System.FilePath × Convex.Module) :=
  [ ("convex/generated/game-api.generated.ts", Convex.module),
    ("convex/generated/schema.generated.ts", Convex.Schema.module Game.Schema.appSchema),
    …
    ("shared/generated/encounter.generated.ts", Game.Encounter.module) ]
```

`lake exe mythroads-emit <root>` writes all of them. Twenty-four files today — the fourteen
per-event handler modules came out when the engine went in, and the six aggregate modules went in
— one process, one place where a path is stated.

The files under `convex/` and `shared/` that are *not* generated are adapters, and they are two
lines each:

```ts
// convex/game.ts
export const dispatch = mutation(dispatchMutationDefinition)
export const execute = internalMutation(executeMutationDefinition)
```

Convex names functions by file path, so these exports preserve `api.game.dispatch`. They do not
reimplement anything.

## 9. The compiled engine

Generating code from Lean *values* still leaves a gap: the emitted TypeScript is a
transcription of the rules rather than the rules themselves. `proofs/Mythroads/Compile/**` closes
it by compiling Lean *functions*.

The design, as its own module documentation states it:

* **Mono-phase LCNF.** The compiler reads Lean's own compiler IR at the `.mono` phase rather than
  the kernel term. By then Lean has erased proofs and types, monomorphised and specialised most
  higher-order code, flattened pattern matching into `cases`, and named every intermediate value.
  What remains is a first-order functional language with join points — very nearly TypeScript
  without mutation — so nothing in the compiler has to think about dependent types, universes, or
  well-founded recursion.
* **A discriminated-union representation.** A Lean structure becomes a plain object; a
  many-constructor inductive becomes a union tagged with `_`, as in `{ _: "lobby" }`; `List` is an
  array; `Nat` and `Int` are `number`; `Option` is `{ _: "none" }` or `{ _: "some", val }`, never
  `undefined`. Every emitted function carries a full signature taken from the LCNF type, so the
  output typechecks under the repository's `strict` configuration instead of drifting into `any`.
* **Loud refusal instead of a plausible file.** The driver refuses to write at all on an unshimmed
  `@[extern]` primitive, on two Lean names claiming one TypeScript identifier, or on a `Nat`
  literal above 2^53.
* **A parity oracle.** The generated file is checked against the Lean `step` itself, scenario by
  scenario and over a seeded fuzz, by exact JSON comparison — the compiler is trusted only as far
  as that oracle agrees.

The executable is [`proofs/Compile.lean`](../../proofs/Compile.lean); its roots are
`Mythroads.Engine.step` plus the six declarations the boundary needs — the four classifiers
(`Event.name`, `Event.authority`, `Event.durable`, `Phase.name`), the refusal table
`Error.message`, and `Lobby.roomCode` for the collision policy — and it writes
`shared/generated/engine.generated.ts` — about seven thousand lines. Nobody maintains that file and
splitting it would cut a strongly connected call graph for no benefit, so it is named in
`scripts/quality/architecture.config.mjs` as the one path exempt from the 300-line limit; Biome's
lint and format rules and `tsc --strict` still apply to it in full.

`convex/generated/aggregate/boundary.generated.ts` calls `step` from this file inside the
`game.dispatch` transaction, so the function a theorem quantifies over and the function Convex
executes are the same definition, translated once and checked against the Lean original by
`tests/engine/engine-parity.test.ts`. Section 6 describes that boundary.

## 10. The checks that keep this honest

```bash
npm run proofs:generate  # rewrite the generated TypeScript from Lean
npm run proofs:check     # build Lean and reject any drift in the generated tree
npm run proofs:axioms    # reject any theorem resting on sorry or on a native_decide axiom
npm run docs:lean        # rewrite lean-definitions.html
npm run check            # the whole gate, including the production build
```

**The drift check.** [`scripts/lean/check-generated.mjs`](../../scripts/lean/check-generated.mjs)
runs the emitter into a staging directory, canonicalises that tree with the repository's own Biome
(the `organizeImports` assist first, then the formatter), and compares it with the repository byte
for byte. Comparing whole trees also catches a generated file left behind after its Lean source was
deleted. The list of files lives in Lean, not in JavaScript.

**The axiom audit.** [`proofs/Axioms.lean`](../../proofs/Axioms.lean) enumerates every theorem
reachable from the `Mythroads` import root, collects the axioms each depends on the way
`#print axioms` does, and fails elaboration if any of them falls outside `propext`, `Quot.sound`
and `Classical.choice`. `sorryAx` means an unfinished proof; `Lean.ofReduceBool` or a minted
`native_decide` axiom means a proof whose evidence is a compiled program's answer rather than a
kernel reduction. The `native_decide` allowlist is **empty**, and the intent is to keep it that
way: every concrete-data fact here — board reachability, catalogue non-emptiness, matchup coverage,
encounter weights — is proved by `decide`, which the kernel checks.

**The documentation.** [`scripts/lean/build-definition-reader.mjs`](../../scripts/lean/build-definition-reader.mjs)
runs `lake exe mythroads-docs`, which imports the compiled modules and reports every authored
declaration with its kind, docstring, elaborated signature, line range, exact source and — for
theorems — its axioms. `npm run docs:lean:check` fails when the rendered page and the sources
disagree, so the reader cannot rot.

## 11. Reading the code: a tour

Read in this order. It is the import order, so nothing refers forward.

1. **[`Engine.lean`](../../proofs/Mythroads/Engine.lean)** — twenty lines of imports and a module
   table that names every file and what it settles. Start here; it is the map.
2. **[`Engine/Core.lean`](../../proofs/Mythroads/Engine/Core.lean)** — `PlayerState`, `Phase`,
   `State`, `Effect`, `Error`. Read the module doc first: it states the three load-bearing design
   decisions (the room is the aggregate, the phase carries its payload, exactly two mutation
   primitives) and those three sentences explain why the proofs later are short.
3. **[`Engine/Room.lean`](../../proofs/Mythroads/Engine/Room.lean)** — `mapPlayer`, `advanceTurn`,
   `draw`, and total board lookup. Small, and everything else depends on it.
4. **[`Engine/Event.lean`](../../proofs/Mythroads/Engine/Event.lean)** — the alphabet and the
   gates. The `#guard`s at the bottom pin the engine's event names, durability and authority to
   `Game.Events.specs`, the manifest the validators are generated from:

   ```lean
   #guard Event.alphabet.map Event.name = Events.specs.map Events.EventSpec.type
   #guard Event.alphabet.map Event.durable = Events.specs.map Events.EventSpec.persistent
   #guard Event.alphabet.map Event.authority = Events.specs.map Events.EventSpec.authority
   ```

   If the engine and the wire protocol ever disagree, the build stops.
5. **[`Engine/Step.lean`](../../proofs/Mythroads/Engine/Step.lean)** — `transition` and `step`.
   Twenty lines that are the whole game.
6. **One phase module**, say [`Engine/Step/Movement.lean`](../../proofs/Mythroads/Engine/Step/Movement.lean),
   to see what an arm of the dispatch actually does.
7. **[`Engine/Theorems.lean`](../../proofs/Mythroads/Engine/Theorems.lean)** — read the module doc
   and then the statements; the proofs are one to three lines each and the statements are the point.
8. **[`Backend/Aggregate/Boundary.lean`](../../proofs/Mythroads/Backend/Aggregate/Boundary.lean)** —
   the transaction that runs all of the above, and the two boundary policies the rules omit. Its
   module documentation is the contract between the engine and Convex.
9. **[`Convex/Ty.lean`](../../proofs/Mythroads/Convex/Ty.lean)** and
   [`Convex/Module.lean`](../../proofs/Mythroads/Convex/Module.lean) if you want to know how a
   generated file is built, and [`Emit.lean`](../../proofs/Emit.lean) for where each one lands.

Every module opens with a `/-! … -/` block explaining its design, and every declaration carries a
`/-- … -/`. That prose is the documentation of record — `lean-definitions.html` renders it, so it
moves with the code it describes instead of drifting in a separate file.

## 12. Extending it safely

1. Add the constructor to `Event`, and let the compiler tell you which of `name`, `authority`,
   `durable`, `permitted`, `onTurn`, `alphabet` and `Error.message` you have not classified.
2. Add the arm to `transition` and the transition itself to the matching `Engine/Step/` module.
3. Add its preservation lemma in `Engine/Preservation.lean`; `ok_transition` will not compile until
   you do.
4. Add its wire shape to `Game/Events.lean` and its translation to
   `Backend/Aggregate/Envelope.lean`; the `#guard`s in both files fail until the two agree.
5. Add a `#guard` in `Engine/Examples.lean` walking the new behaviour concretely.
6. Regenerate (`npm run proofs:generate`), review the TypeScript diff, and run `npm run check`.

The payoff is the same in every case: the Lean value a theorem talks about is the value the
generator consumes, so a proof cannot describe one policy while production runs another.

The architectural decision behind all of this is recorded in [`formal-rules.md`](formal-rules.md);
the longer migration plan is in [`lean-full-backend-plan.md`](lean-full-backend-plan.md).
